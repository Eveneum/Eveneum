# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project Overview

Eveneum is a simple, developer-friendly Event Store with snapshots, backed by Azure Cosmos DB. It has been in production use since Oct 2018 and is considered stable — treat changes conservatively and preserve public API compatibility.

Core capabilities:

- Write/read streams of events in a single call (retries and batching handled internally)
- Snapshots: create, read (with optional consecutive events), delete
- Optimistic concurrency via `expectedVersion` on writes/deletes
- Customizable Cosmos DB document schema for rich querying
- Change-feed-friendly document design for independent projections

```
Directory.Packages.props  Central Package Management versions
azure-pipelines.yaml      Azure DevOps CI
GitVersion.yml            GitVersion (GitHub Flow, trunk = master)
```

Key areas inside `Eveneum/`:

- `IEventStore.cs` / `EventStore.cs` — public API (`Initialize`, `ReadStream`, `ReadHeader`, `WriteToStream`, `DeleteStream`, `CreateSnapshot`, `DeleteSnapshots`)
- `Documents/EveneumDocument.cs` — Cosmos document schema (single container, `/StreamId` partition key; document types: header, event, snapshot)
- `Persistence/` — Cosmos persistence layer
- `Serialization/` — JSON serialization abstractions (`IJsonSerializer`, `ITypeProvider`, document converters)
- `Exceptions/` — all exceptions derive from `EveneumException`
- `StoredProcedures/BulkDelete.js` — embedded stored procedure (EmbeddedResource)

## Build & Test

```powershell
dotnet build Eveneum.sln -c Release
dotnet test Eveneum.Tests
```

### Running tests

Tests require a **running Azure Cosmos DB emulator**:

- Windows: `Import-Module "C:\Program Files\Azure Cosmos DB Emulator\PSModules\Microsoft.Azure.CosmosDB.Emulator"; Start-CosmosDbEmulator -Timeout 600`
- Default endpoint `https://localhost:8081` with the well-known emulator master key
- Overridable via **user-level** environment variables (see `Eveneum.Tests/Infrastructure/CosmosSetup.cs` and `ScenarioDependencies.cs`):
  - `CosmosDbEmulator.Endpoint`
  - `CosmosDbEmulator.Key`
  - `CosmosDbEmulator.ConnectionMode` (`Direct` or `Gateway`)
  - `CosmosDbEmulator.OS` (`Windows`, `Linux`, or `Windows,Linux` — selects which test contexts run)

Each scenario is executed against multiple `CosmosDbContext` implementations (Newtonsoft.Json vs System.Text.Json, Windows vs Linux emulator), all in parallel. When fixing a failing test, verify the failure is not emulator-specific.

## Testing Conventions

- BDD tests use **Reqnroll** (`.feature` files) with **NUnit** step definitions (`[Binding]` classes) and DI via `Reqnroll.Microsoft.Extensions.DependencyInjection`
- `*.feature.cs` files are auto-generated by `Reqnroll.Tools.MsBuild.Generation` — **do not edit them manually**; edit the `.feature` file and/or step definitions instead
- Shared test state lives in `Eveneum.Tests/Infrastructure/` (`CosmosDbContext`, `CosmosSetup`, `ScenarioDependencies`)
- Sample event/snapshot types for scenarios are in `Eveneum.Tests/Sample.cs`

## Conventions

- **Central Package Management**: add/update package versions only in `Directory.Packages.props`; `PackageReference` items in csproj files must not specify `Version`
- Target frameworks: libraries `netstandard2.0` with `LangVersion latest` and `GenerateAssemblyInfo false`; tests `net10.0`. Do not raise library target frameworks without explicit request
- Block-scoped namespaces (`namespace Eveneum { ... }`), matching existing style
- C# latest language features are in use (e.g. primary constructors in tests)
- The codebase contains essentially no comments; do not add comments unless requested
- New public exceptions must derive from `EveneumException` and live in `Eveneum/Exceptions/`
- Preserve the change-feed-friendly document shape in `Documents/EveneumDocument.cs`; changes to the stored schema affect existing production databases

## CI & Packaging

- CI (`azure-pipelines.yaml`): Windows 2025 agent → GitVersion → restore/build (Release) → `dotnet pack` of the three libraries from their `.nuspec` files → start Cosmos emulator → VSTest with code coverage
- Versioning is GitVersion (GitHub Flow; `trunk`) — do not hardcode versions
- Each packable project has its own `.nuspec` (e.g. `Eveneum/Eveneum.nuspec`); update it when adding/removing package dependencies
